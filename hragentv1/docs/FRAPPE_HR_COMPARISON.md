# HRAgent 与 Frappe HR 的路线选择

更新时间：2026-07-13

## 结论

HRAgent 保留 Vue 3 + Spring Boot + MySQL + Redis 技术栈，把 Frappe HR 当作产品和交互蓝图，不直接复制 Frappe HR 业务代码，也不在当前阶段替换成 Frappe Framework。

这不是因为 Frappe HR 不好，而是因为它的成熟能力和底层框架绑定得很深。把它“套进”当前项目，并不像替换一套网页主题，而更像更换整栋楼的承重结构。

## 核对到的 Frappe HR 事实

2026-07-13 查看 `frappe/hrms` 公开仓库时：

- 默认开发分支为 `develop`，仓库已有约 10,823 次提交、319 个 release，最新展示版本为 `v15.62.2`。
- 仓库使用 GPL-3.0 许可证。
- 主要语言为 Python，管理后台依赖 Frappe Framework 的 DocType、权限、工作流、报表和 REST API 能力。
- 单独的员工端前端使用 Vue 3、Frappe UI、Ionic、Tailwind、PWA 和 Firebase。
- Frappe UI 组件库本身使用 MIT 许可证，但它不是 Frappe HR 完整管理后台的模板。

以上数字会随项目继续开发而变化，仓库地址为 <https://github.com/frappe/hrms>。

## 为什么不能直接套模板

Frappe HR 管理端的大量页面不是一批独立 Vue 页面，而是由 Frappe Framework 根据 DocType 元数据、角色权限、工作流和报表配置动态生成。直接复制页面会缺少它背后的数据模型和运行时。

当前 HRAgent 的后端是 Java Spring Boot，Frappe HR 的后端是 Python/Frappe。直接使用完整 Frappe HR，需要同时更换：

- 数据模型和数据库迁移体系
- 登录、会话和权限模型
- 审批工作流
- API 约定
- Docker 服务组成和部署方式
- 后续开发所需的主要语言和框架

这会让当前 Spring Boot 代码大部分失去作用。

## 可以复用什么

推荐复用：

- 产品模块划分：员工生命周期、请假与考勤、审批、报表、通知、设置。
- 信息架构：工作区、列表、表单详情、筛选器、状态流、快捷操作。
- 业务规则设计：假期政策、节假日、分配周期、多级审批、附件、委托审批。
- 交互方式：高密度表格、统一状态颜色、可保存筛选、批量操作、时间线和审计记录。

谨慎复用：

- Frappe UI 是 MIT 许可，可以依法使用，但当前项目已经使用 Element Plus。两套组件库并存会增加样式、体积和维护成本，因此暂不引入。
- Frappe HR 的 GPL-3.0 代码不直接复制到当前产品。若未来确实复制或修改并向客户分发，需要单独评估 GPL 的源代码提供义务和商标政策。这里不是法律意见，商业发布前应做正式许可证审查。

## 两条可选技术路线

### 路线 A：继续建设 HRAgent

优点：保留用户指定的 Java 技术栈，智能体和 API 能按自己的产品目标设计，已有代码可以继续使用。

代价：权限、工作流、通知、报表、迁移、测试和运维能力需要逐步补齐。

这是当前选择。

### 路线 B：以 Frappe HR 为主系统

优点：立即获得成熟 HRMS 的大部分模块。

代价：核心后端切换到 Python/Frappe；需要重新做中文本地化、国内通知渠道、SaaS 租户运营和智能体扩展；当前 Spring Boot 主系统不再是核心。

如果以后验证发现“完整 HRMS”比“独特的 HR Agent SaaS”更重要，可以另开验证分支运行 Frappe HR，而不是把两套系统混在一个代码库里。

## HRAgent 后续对标顺序

1. 配置中心、权限点和安全基线。
2. 假期政策、节假日和可配置审批流。
3. 通知中心、待办和审批时间线。
4. 报表、筛选、导出和导入失败回执。
5. 多租户注册、公司空间、邀请和租户管理员。
6. Flyway 数据迁移、自动化测试、备份、监控和生产部署。
7. 在稳定 HR 数据与流程之上增加 Agent 配置、工具调用、评估和审计。
